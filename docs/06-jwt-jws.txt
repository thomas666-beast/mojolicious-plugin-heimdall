JWT: SIGNED API ACCESS TOKENS
=============================

Signing lets a verifier check integrity and authenticity. It does not
hide the claims. Do not put passwords or other sensitive data in a token.
Use TLS and send tokens in the Authorization header, not in query strings.

Configure an independent random signing key of at least 32 bytes for
HS256. Do not use the same key for signing session cookies. Read it from
application secrets, not source control.

ISSUE AFTER VERIFYING THE USER

  my $issuer   = 'https://accounts.example.test';
  my $audience = 'example-api';
  my $jwt      = $c->heimdall->jwt;
  my $bearer   = $jwt->encode({
    iss => $issuer, aud => $audience, sub => "$user_id", exp => time + 300,
  }, $key, 'HS256');

This snippet belongs in your authenticated token-issuance flow, after you
have established $user_id. Do not expose a route that issues tokens for
arbitrary subjects.

VERIFY ON EACH API REQUEST

  my $header = $c->req->headers->authorization // '';
  my ($bearer) = $header =~ /\ABearer ([A-Za-z0-9_.-]+)\z/i;
  my $claims = eval {
    $c->heimdall->jwt->verify_access_token(
      $bearer, $key,
      alg => 'HS256', issuer => $issuer, audience => $audience,
    );
  };
  return $c->render(json => {error => 'unauthorized'}, status => 401)
    unless $claims;

Only use a key, algorithm, issuer and audience set by your application.
The method rejects tokens missing an expiration, expected issuer,
expected audience or nonempty subject. It does not confirm an account
still exists or grant any permissions. Look up $claims->{sub} and enforce
account status and authorization before processing the request.

For lower-level or legacy JWS use, `decode` defaults to HS256 and accepts
an explicit algorithm allowlist. It does not require the access-token
claims. Pass PEM keys as scalar references or supported key objects,
not as HMAC secrets. JWE has a separate helper described in document 07.

JWT best practices: https://www.rfc-editor.org/info/rfc8725/
