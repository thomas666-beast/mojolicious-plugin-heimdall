SECURITY CHECKLIST
==================

Before you deploy, confirm every item below.

1. SESSION SECRET
   app->secrets(['...']) is set to a value of at least 32 random
   bytes per key, loaded from configured secrets, not hard-coded.
   Do not use the Mojolicious default. Keep signing and verification
   keys private, including old keys during rotation.

2. JWT / HMAC SECRET
   The HS256 key is at least 32 bytes, from the environment, and
   different from the session secret.

3. JWT DECODE ARGUMENTS
   For API authentication, use verify_access_token with the expected
   issuer, audience and algorithm. Resolve the subject to an active
   account and authorize the action separately. For low-level decode
   and decode_jwe, configure algorithm allowlists independently of
   the token. Never put a bearer token in a URL.

4. RSA PRIVATE KEY
   Stored outside the application tree, file mode 0600, never in
   git. If it leaks, rotate it: generate a new pair and re-encrypt
   anything that was wrapped with the old public key.

5. AES KEY
   32 random bytes, from the environment, unique per deployment,
   never reused across applications.

6. PASSWORD COLUMN
   Long enough to hold a full Argon2 hash (255 characters is safe).
   Comparisons happen through $h->password->verify(), not == or eq.

7. RANDOM VALUES
   No rand(), no int(rand()), no time(). Only $h->random->*.

8. LOG OUTPUT
   No password, hash, key, token, or private key in logs. Check that
   your exception handler does not print stack traces containing
   secrets to the client.

9. HTTPS
   In production, run behind TLS. Sessions, JWTs, and credentials
   must not travel over plain HTTP.

10. DEPENDENCY VERSIONS
    Heimdall requires Mojolicious >= 9.48 and CryptX >= 0.091.
    Keep them and Crypt::JWT up to date. Confirm CryptX with:

      perl -MCryptX -e 'print $CryptX::VERSION, "\n"'

11. COOKIE FLAGS
    In production set:

      app->sessions->secure(1);
      app->sessions->samesite('Lax');

    Secure limits the cookie to HTTPS. SameSite=Lax restricts some,
    but not all, cross-site requests. Keep CSRF protection enabled.

12. LOGIN AND LOGOUT
    Use POST and validate a CSRF token for both. Throttle login attempts.
    Return the same failure message for unknown users and wrong passwords.
    Validate that the user is active on protected requests. For immediate
    revocation of already-issued cookies, add server-side sessions or
    an app-level revocation check.

13. TESTS AND RELEASE
    Run the full test suite before every release:

      prove -lr t xt
      perl Makefile.PL
      make dist

    Install the archive into a fresh local lib, not just the source tree.
    Verify the packaged version and re-run the example.
